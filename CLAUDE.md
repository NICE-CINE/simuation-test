```bash
# Setup (first time)
python3 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"

# Run the simulator (prints the report and archives it, see below)
python main.py

# Run all tests
pytest

# Run a single test file / test
pytest tests/test_network.py -v
pytest tests/test_network.py::test_network_engine_two_hop_relay_takes_two_intervals -v

# Compare every routing algo x {with, without beacons}, same seed, in parallel
python scripts/compare_algorithms.py --seed 42 --duration 3600 \
    --num-festivaliers 200 --beacon-count 6 --workers 2 [--csv out.csv]

# Same matrix over several paired seeds: one CSV row per run + a <...>_comparaison_resume.csv (mean, Student 95 % CI half-width per metric)
python scripts/compare_algorithms.py --seeds 1 2 3 4 5 --duration 3600 --num-festivaliers 200 --workers 12
# ... or only some algorithms
python scripts/compare_algorithms.py --algorithms tide fresh_spray spray_wait --seeds 1 2 3 4 5

# Sweep fresh_spray's initial_tokens over seeds (per-token means at the end)
python scripts/sweep_fresh_spray_tokens.py --tokens 4 8 16 32 --seeds 1 2 3 \
    --duration 10800 --num-festivaliers 5000 --beacon-count 6 --workers 12 \
    --mobility poi --reply-probability 0.5

# Compare band_fanout variants (defaults, no purge, no band, fanout, max_hops) over seeds
python scripts/sweep_band_fanout.py --seeds 1 2 3 --duration 3600 --num-festivaliers 500 \
    --beacon-count 6 --workers 12 --mobility poi --reply-probability 0.5 \
    [--variant "fanout=2,max_hops=4" ...]
```

Every run of these scripts is archived in `archives/` (`--archive-dir` to override; tests must pass a `tmp_path` so they don't pollute it) via `festival_ble_sim/archive.py`: `<YYYY-MM-DD_HH-MM-SS>_<algo>.txt` for `main.py`, `replay/<same stem as the .txt>.html` + `.data.js` for `main.py --replay-html`, `<...>_comparaison.csv` for the comparison, `<...>_sweep_fresh_spray_tokens.csv` for the token sweep (`initial_tokens` lives only in the CLI args part of its `.json`), `<...>_sweep_band_fanout.csv` for the band_fanout variants (the variant strings live only in the `.json` CLI args), each with a same-named `.json` holding the CLI args, the fully resolved `SimulationConfig` (config defaults drift over time, so args alone can't reproduce a run) *and* `git` (`commit`, `dirty`, porcelain `status`, `diff` against HEAD — untracked files are only listed, so commit a script before archiving runs made with it). `archive_stem` reserves the stem by creating the `.json` exclusively, so two runs in the same second get `<stem>` and `<stem>-2`. `--output`/`--csv` only write an extra copy. `archives/2026-09-28-comparaison.csv` predates this naming and has no `.json`.

Pre-naming archives without a `.json`: `archives/2026-09-21-comparaison.csv` (formerly `comparaison.csv` at the repo root). Replays (`archives/replay/`, the `.html` and its `.data.js` together) are meant to be committed.

CI: `.github/workflows/tests.yml` runs `ruff check .` then `pytest` on Python 3.9 and 3.12 on every push and PR.

Lint: `ruff check .` (`--fix` for the auto-fixable ones), errors only (`select = ["F"]`: undefined names, unused imports/variables…); ruff's broader defaults fight the conventions below (e.g. they push `X | None`), so widen the selection rule by rule. No formatter.

## Architecture

A discrete-event SimPy simulation of opportunistic BLE mesh messaging (`src/festival_ble_sim/`). Built bottom-up as pure, independently-testable modules that only get wired together in `simulation.py`:

```
models.py, config.py          — leaf modules, no internal deps
  ↓
spatial.py, energy.py, radio.py — depend only on models/config
  ↓
mobility/, routing/           — pluggable Strategy interfaces (ABCs).
                                 Both only reference `nodes.BaseNode` under
                                 `TYPE_CHECKING` and duck-type against it at
                                 runtime, so they have zero runtime coupling
                                 to nodes.py.
  ↓
nodes.py                      — BaseNode/MobileNode/BeaconNode; the concrete
                                 type mobility/routing were duck-typing against
  ↓
beacons.py, metrics.py, traffic.py, network.py
  ↓
simulation.py                 — run_simulation(config, routing_algorithm=None,
                                 mobility_factory=None, history=None,
                                 progress_callback=None,
                                 progress_interval_s=10.0) wires everything
                                 into one SimPy env.run() and returns a
                                 SimulationReport
  ↓
viz/history.py, viz/replay.py — optional: SimulationHistory is a plain data
                                 container simulation.py/network.py populate
                                 when a caller passes one in; replay.py
                                 renders it to a small HTML page plus a sibling
                                 `<stem>.data.js` (loaded by <script src>, since
                                 fetch() of a JSON fails on file://). Positions
                                 are decimetre ints thinned by
                                 `snapshot_every_ticks`, events columnar
                                 (`CompactEventLog`) and sampled to
                                 `--replay-max-messages` full messages. Neither
                                 is imported by the core engine unless a
                                 caller opts in.
```

`radio.py` holds the log-distance path-loss model (`max_range_m`, `received_power_dbm`, `link_margin_db`) that both `simulation.py` (to size `SpatialGrid` and each node's `radio_range_m` from `BleConfig.phone_radio`/`beacon_radio`) and `network.py` (to derive the weak-signal/shadowing component of packet loss from each sender/contact pair's link margin) build on. `RadioParams.shadowing_std_db` makes `received_power_dbm`/`link_margin_db` stochastic per call when given an `rng` — 0.0 (the dataclass default, though not `BleConfig`'s actual phone/beacon radio defaults) reproduces the old deterministic behavior.

`main.py` is a thin CLI: build a `SimulationConfig`, call `run_simulation`, `format_report`, print + archive it (see above), optionally `render_replay_html` when the `--replay-html` flag is set (written next to the report as `<stem>.html`). Algorithms are selected (`--routing`) from the shared registry `routing/registry.py` (`ROUTING_NAMES`, `build_routing(name, seed, spray_initial_copies=8)`), which every script uses so one `--seed` seeds the algorithm the same way everywhere.

`scripts/compare_algorithms.py` runs the {algorithm} x {with/without beacons} matrix through a `ProcessPoolExecutor` (`--workers`), using `run_simulation`'s `progress_callback` for a live status line, and appends each finished row to the CSV as it completes. Its `ALGORITHMS` is the registry's `ROUTING_NAMES`, built with `build_routing(name, seed)`.

### Traffic

Each `MobileNode` gets its own `traffic.traffic_process` with a fixed personal rate drawn once from `TrafficConfig.messages_per_hour_range` (default `(0.0, 4.0)`; a node drawing 0 never sends). Total load therefore scales with `num_festivaliers` — there is no network-wide `mean_interval_s` anymore. Destination is a uniformly random active *friend* (`TrafficConfig.friends_only`, default `True`; `False` restores a uniformly random other active node). Friend groups come from one shared graph, `social.assign_friend_groups` driven by `SimulationConfig.social`, set on each `MobileNode.friends` before `on_simulation_start` — `bubble_f` reads it from there rather than generating its own. Friendless people (`no_friend_fraction`, default 20 %) send nothing. Nobody texts a friend in sight: friends closer than `TrafficConfig.skip_friends_within_m` (15 m, ground truth) are not drawn as destinations. `TrafficConfig.reply_probability` (default 0, `--reply-probability` in both scripts) makes a delivered message spawn a reply from its destination after `reply_delay_range_s`, via `network_engine`'s `on_delivery` callback; its RNG is only drawn when > 0, so runs without replies are unchanged. Replies carry `Message.is_reply=True` and are reported apart (`replies_created/delivered`, `reply_delivery_ratio`): `delivery_ratio`, latency and hops cover spontaneous messages only (followups included), the set every algorithm sees at a given seed; `overhead` covers all traffic. `TrafficConfig.followup_probability` (default 0, `--followup-probability`) adds bursts: after each spontaneous message the sender writes again to the same destination (geometric chain, delay from `followup_delay_range_s`), from its own `random.Random(f"{seed}-followup")` that exists only when > 0.

### Energy

`EnergyConfig` is calibrated on the Nice Mesh radio bench (12 Oct 2026, two phones, Nearby Connections P2P_CLUSTER); every value, its derivation and whether it is measured or estimated live in `docs/energie/consommation.md` — update both together. Each active phone pays `background_current_ma` (31 mA, being reachable) + `phone_current_ma` (82 mA, the phone itself incl. a screen share whose overhead is measured but whose 20 % on-time is estimated; 0 = mesh only) per tick in `simulation._mobile_process`, which dominates the report's energy; tx/rx are billed per transmission in `network.py` (RX ≈ 4× cheaper than TX). Connections cost energy too (`network._update_connections` / `network_engine`): `connection_setup_mah` (7 s at the measured advertising+scan overhead) on both ends when one opens, and `extra_connection_current_ma` (3 mA, estimated) per tick for each connection a phone holds beyond the first. The report also has a *mesh* energy (`total/avg_mesh_energy_consumed_mah`, in the comparison CSV): everything except `phone_current_ma`, the column to compare algorithms on. Only `consume_energy(mah, mesh=False)` (the phone draw) is excluded, so new algorithm-billed costs count as mesh by default. Capacity is `battery_capacity_mah` (4500); `initial_charge_bins` (`(share, lo, hi)` tuples, default one fixed full bin = no draw) sets each phone's starting charge, drawn by `simulation.draw_charge_fraction` from its own `random.Random(f"{seed}-charge")` (always created; the default bin draws exactly 1.0) so it never shifts other draws. `--random-charge` (`main.py`, `compare_algorithms.py` via `presets.add_random_charge_argument`/`energy_config`; not the sweeps) applies `presets.FESTIVAL_CHARGE_BINS` (50 % at 80–100 %, 30 % at 50–80, 12 % at 30–50, 8 % at 5–30).

### Measurement window

`SimulationConfig.cooldown_s` (default 0; `--cooldown` in `main.py`/`compare_algorithms.py`, defaulting to the message TTL there and in the sweeps via `compare_algorithms.build_config`) runs the simulation `duration_s + cooldown_s`, traffic included, while `MetricsCollector(measure_until=duration_s)` only counts creations, deliveries, transmissions and losses of messages created before `duration_s`. Engine `metrics.record_*` calls must pass the message so this filter works. Energy, dead nodes and evictions cover the whole run.

`SimulationConfig.warmup_s` (default 0; `--warmup` in `main.py`/`compare_algorithms.py`, defaulting to `presets.DEFAULT_WARMUP_S` = the longest pause, 2700 s, there and in the sweeps via `compare_algorithms.build_config`) runs mobility alone first: `simulation._after` delays the network engine, traffic, churn times and the history recorder by it, `_mobile_process` bills no energy before it, and `MetricsCollector(measure_until=warmup_s + duration_s)`. Encounter tables start empty when it ends (the engine doesn't run during it: neighbor queries are the run's main cost). `SimulationConfig.total_s` = warm-up + duration + cooldown; scripts size their progress bars on it.

### GPS

Engine-provided, so position-unaware algorithms are unaffected:
- `node.gps_fix()` — `gps_position()` that returns `None` with `GpsConfig.fix_failure_probability` (`--gps-fix-failure`, drawn only when > 0). Use it wherever a *fix* is taken (message creation, algorithms' GPS rounds).
- `node.gps_position()` — noisy reading (`GpsConfig.noise_std_m`, default 5 m, resampled per call from one shared seeded RNG); beacons and σ=0 read exact. Use it for the holder and its neighbors (`contact` in `decide`, `neighbors_by_node` in `on_tick`); `node.position` is the ground-truth oracle.
- `message.src_position` — source's GPS at creation. On delivery `network.py` stores it in the destination's `known_positions[src_id] = (position, creation_time)` (newest wins).
- `message.dst_position` / `dst_position_time` — source's last known position of the destination at creation, i.e. from the destination's last message delivered to the source. `None` when unknown (frequent: no replies are simulated) — geographic algorithms must fall back to a non-geographic decision.

### Extension points (Strategy pattern)

- **Routing:** subclass `routing.base.RoutingAlgorithm`, implement `decide(message, holder, contact, now) -> RoutingDecision`. Optional hooks (all no-op by default): `on_simulation_start(nodes)`, `on_tick(now, neighbors_by_node)` (every in-range pair each tick, even with nothing to send — needed by contact-history algorithms; only fired when the engine has a `ble_config`, which `run_simulation` always passes), `on_delivered(message, holder)`, `on_forward(message, holder, contact, forwarded_copy)` (split per-copy `routing_state`, e.g. Spray & Wait tokens), `select_links(sender, neighbors, max_links)` (which neighbors get the `max_concurrent_links` slots; default = destinations of the sender's messages first, then nearest), `choose_eviction(node, now) -> Optional[int]` (victim when a forwarded copy lands in a full buffer; `None`/unknown id falls back to `BaseNode.store_message`'s FIFO). Pass a custom instance via `run_simulation(config, routing_algorithm=MyRouting())`, and register it in `routing/registry.py`'s `_FACTORIES` (factory takes `(seed, spray_initial_copies)`).
  - Implemented: `epidemic` (reference, naive flooding), `spray_wait`, `prophet`, `beacon_priority`, `dasfv` (DASF-V, density-aware spray-and-focus + ack purge), `gossip_a` (GOSSIP-A, density-adaptive probabilistic gossip + its own epidemic purge tokens, billed as a 128-byte PURGE_SYNC Bloom per connection, not the engine acks + replicated-first eviction), `bubble_f` (BUBBLE-F, social bubble routing seeded from a generated friend graph), `managed_flood` (Bluetooth Mesh managed flooding: TTL + per-node message cache + relay window, no store-carry-forward, PDUs over the connectionless advertising bearer (`advertising_bearer = True`: `network._broadcast_messages` sends each message once to every neighbor `decide` picks, advertising-channel load, receptions lost not resent, no connections); ranks all neighbors (skipping those that already hold or are the destination of every pending message) and overrides `select_links` so destinations, then its chosen relays, take link slots ahead of the nearest ones (the `max_concurrent_links` cap still holds); Used by `horizon` (vectors), `eco_sf` (Trickle beacons), `managed_flood`/`bitchat` (flooded acks; bitchat announces too); with `{}` (default) the engine makes no extra rng draw.
  - Optional hooks `on_energy_model(energy_model)` / `on_ble_config(ble_config)`: the run's `EnergyModel` and `BleConfig`, called by `run_simulation` right after `on_simulation_start`, for algorithms that bill or size extra traffic themselves (`managed_flood`'s delivery-hop ack, `bitchat`'s announce cap).
  - Delivery acks and summaries (`network._exchange_metadata`, every tick on every ready connection, before data, billed like data on that link — airtime, retransmissions, energy, channel duty; skipped whole and retried next tick if it doesn't fit): each side's summary vector (`BleConfig.summary_id_bytes`=4 per id of buffer ∪ `delivered_ids` (∪ `outbox` with acks) not yet listed on that `_Connection`), the acks the peer asks for (ids it lists that this side has in `acked`, `ack_size_bytes` each, 8 by default) and, once per connection, `connection_table_bytes(node, peer)` (default 0; `routing.base.per_destination_table_bytes` = 8 per destination the peer carries). Acks only flow when the algorithm sets `uses_delivery_acks = True`: the destination mints one on delivery and acks the delivering holder at once; a node that learns one (`BaseNode.learn_ack`) drops its copy and its `outbox` entry; beacons share theirs over the backhaul. `BaseNode.acked`/`outbox` (`msg_id -> expiry`, filled by `traffic.py` for own messages) are pruned with the buffer. `has_message` includes `acked`. There is no global "delivered" set any more: an algorithm only knows what reached the node.
  - One instance is shared by every node for the whole run, so an algorithm can hold global observation state (contact tables, density, communities) instead of simulating beacon/bloom wire formats — by design, but what `decide` reads about a contact must be billed through `connection_table_bytes`, and delivery knowledge goes through the engine acks, never a shared set. `gossip_a`/`bubble_f`/`tide` take a `seed` for their own RNG; keep them deterministic from it.
  - `decide()` returning FORWARD is only an intention: the engine checks the airtime budget and draws packet loss *after* it, and a dropped copy gets no `on_forward`. State that assumes the copy arrived (token splits, flags like `beacon_priority`'s `reached_beacon`, removing the holder's copy) goes in `on_forward`/`on_delivered`; the `_forward_reason` pattern (set in `decide`, consumed in `on_forward`) is fine since the next `decide` overwrites it.
  - Algorithms may `pop` from `holder.buffer` (purges, copy-exhausted handoff) inside `decide`/`on_forward`/`on_tick`. Safe only because the engine iterates the tick snapshot, not the live buffer (see invariants below).
- **Mobility trap:** `run_simulation` uses `RandomWaypointMobility` unless given a `mobility_factory`, even when `config.mobility` has POIs. `main.py`, `compare_algorithms.py` and the sweeps go through `presets.mobility_factory(name, config.mobility)` (`MOBILITY_MODELS`: `random_waypoint`, `poi`, `group`; `--size` defaults to `group`); an ad-hoc script that only builds the config silently simulates random waypoint (very different numbers: 43 % vs 60 % of destinations in the source's component at 500 people).
- **Mobility:** subclass `mobility.base.MobilityModel`, implement `initial_position(area)` and `step(current, dt, area)`. Reference impls: `mobility/random_waypoint.py` (uniform target), `mobility/group.py` (`GroupMobility`, friends move together: the first member (by id) on site and with the group leads with `PoiMobility` and keeps the lead until it leaves the site (a shared `_Team`), members keep an offset within `GroupConfig.radius_m`, leave alone for short/long trips after fixing a rendezvous at their current spot and the trip's end, where the leader waits `rendezvous_max_wait_s` (as long as the member's `_RETURN` state lasts), else search POIs until within `visual_range_m` of the leader, as does a member arriving on site after its group; independent of the simulated mesh on purpose; bound by `run_simulation` through the `MobilityModel.join_group(node, members)` hook, called on every member once friend groups are drawn, which may return the member's start position) and `mobility/poi.py` (`PoiMobility`, targets weighted `MobilityConfig.points_of_interest`, requires at least one with positive weight; `MobilityConfig.background_probability`, `None` by default, mixes uniform visits into both initial positions and targets). Site presets live in `presets.py` (`--size` in `main.py` and both scripts: festivaliers + area at ~3 m²/person, `dense_zone_pois` = POIs covering 15 % of the site, `crowd_mobility_config` sets `background_probability` for a 70 % dense-zone target share; `resolve_cli_args` makes `--num-festivaliers`/`--mobility` default to `None` so `--size` can detect conflicts). Each `MobileNode` owns its own instance; inject a custom one via `run_simulation(config, mobility_factory=lambda rng: MyMobility(rng))` — a *factory*, not an instance, because each node needs its own stateful model seeded from its own RNG.
- **Beacon placement:** `beacons.place_beacons(area, beacons)` — `"grid"` (regular grid, default) or `"manual"` (explicit coordinates). Not a Strategy class, just a two-branch function.

### Network engine realism layers (`network.py`)

All opt-in/no-op when the relevant config/param is `None` or its default, so existing callers (including most tests) are unaffected. Every layer is engine-level — applies uniformly to whatever `RoutingAlgorithm` is plugged in, not something each algorithm has to implement itself:

- **Channel (`ChannelState`, `_link_failure_probability`):** each node's duty (bytes it put on the air last tick / its airtime budget, data and control apart) and the summed duty it hears from its neighbors, rebuilt each tick by `ChannelState.next_tick` (only actual sends count, never mere buffer contents). A packet's failure probability combines `packet_loss_base_probability`, the weak-signal term near the edge of range and collisions `1 - exp(-heard load minus the sender's own duty / channels)` (`data_channels=79`, Bluetooth Classic hopping; `advertising_channels=3`), with no cap: a packed crowd saturates. On a connection a failure p is resent, costing `1/(1-p)` times the airtime and tx/rx energy (`retransmitted_bytes`) instead of dropping the message; there is no CSMA backoff anymore.
- **Airtime (`airtime_left`):** `transfer_rate_bytes_per_s * contact_check_interval_s` bytes per *radio* per tick (37 kB/s, measured Nearby throughput between two phones alone; the crowd acts through the channel load, not this figure), shared by all of a node's sends and receives; `network_engine` holds one dict per tick and processes senders in an rng-shuffled order so no node id always wins a busy receiver. Neighbor lists (`_active_nearby`) only ever contain active nodes — the grid itself still holds inactive ones.
- **Connections (`_update_connections`, `_link_radio`):** range is mutual (`_active_nearby` keeps a neighbor only if each is within the other's range, so a beacon can't push to a phone that can't answer) and a link's loss uses its weaker direction's radio. Connections persist across ticks in `network_engine` (`(low id, high id) -> [ready_at, last_used]`): two-way, counting against both ends' `max_concurrent_links`, opened in the shuffled order by nodes with something to send (`select_links` picks among neighbors with a free slot), usable only `BleConfig.connection_setup_s` (7 s, measured Nearby discovery-to-connection) after opening, kept while both stay in range and active, closed after `connection_idle_timeout_s` (30 s, estimated) without data. Each node's ready links are passed as `process_node_contacts`'s `neighbors` (which then skips `select_links`; it only picks links itself when called without `neighbors`, as unit tests do), and it returns the contacts it sent to, which refreshes `last_used`. Engine tests that expect a first-tick exchange set `connection_setup_s=0.0`.
- **Hop-count TTL (`Message.ttl_hops`/`hop_limit_reached()`):** gates the `FORWARD` branch only, never the direct-delivery-to-destination branch — a hop-exhausted message stops spreading but can still reach its destination in one more hop, matching Spray & Wait's existing "wait phase" pattern.
- **Shadowing-driven outage:** `link_margin_db(..., rng)` can sample negative even inside the deterministic max range; the link then carries nothing that tick (failure 1.0, no resend can help).
- **Beacon backhaul latency/loss (`beacon_backhaul_relay`):** per-tick attempt probability (`contact_check_interval_s / backhaul_latency_s`) instead of a delivery queue, so a message not attempted (or lost) this tick is retried automatically next tick — no extra state to track.

### Churn

`ChurnConfig` (`SimulationConfig.churn`, disabled by default) staggers each mobile node's arrival/departure via `simulation._churn_process`, toggling the *same* `is_active` flag that battery depletion, network participation, and traffic src/dst eligibility already gate — not a parallel "presence" mechanism. `BaseNode.battery_depleted` is a separate flag (set only by `consume_energy` hitting zero) so the report's `dead_node_count` isn't inflated by ordinary churn departures; don't compute it from `not is_active` again.

### Correctness invariants that are easy to break

- **`network.py` computes neighbors once per tick.** `_compute_neighbors` does one `SpatialGrid.get_nearby` per active node and the result is shared by `on_tick`, `_compute_contention_counts`, and each `process_node_contacts` call (via its `neighbors` param). Don't re-query the grid per node — it roughly doubled runtime at scale. Likewise `SpatialGrid` cells are sized to the *phone* range (not max(phone, beacon)), and threshold/sort comparisons use `Position.distance_squared_to` to skip the sqrt.
- **No iteration over a `set` of node (or any default-hashed) objects.** Their hash is their `id()`, i.e. memory layout, so the order changes between runs with the same seed. `SpatialGrid` cells are insertion-ordered dicts for that reason: with sets, neighbor order (and `bitchat`'s first-arrival announce BFS) differed between identical runs. Sets of ints are fine.
- **`network.py`'s tick-snapshot ordering.** `network_engine` snapshots every node's buffer *before* processing any node that tick, and `process_node_contacts` iterates that snapshot rather than the live buffer. This is load-bearing: without it, a node processed later in the same tick would immediately relay a message it received earlier that same tick, collapsing multi-hop delivery into one timestep and making results depend on dict iteration order. `process_node_contacts` has a `messages=None` default (→ falls back to `list(sender.buffer.values())`) purely so the single-node unit tests in `tests/test_network.py` can call it directly without going through `network_engine`.
- **Message copies must be independent.** Forwarding uses `dataclasses.replace(message, hops=message.hops+1, routing_state=dict(message.routing_state))` — never mutate `message.hops` in place, and always copy `routing_state` (it's a `Dict[str, Any]` bag reserved for future per-copy algorithm state, e.g. Spray & Wait's `copies_left`). A shared/mutated original would corrupt hop counts or state in every other buffer still holding a reference to it.
- **`BaseNode.battery_mah == math.inf`** is the sentinel for unlimited power (default for beacons). `consume_energy` no-ops on it; `energy_consumed_mah` returns `0.0` for it; the final report's energy average filters these nodes out via `battery_capacity_mah != math.inf`. Don't treat `inf` as a normal float in new energy-related code.
- **Battery capacity vs starting charge.** `BaseNode(battery_mah=...)` is the *capacity* (`battery_capacity_mah`, 100 %); the node starts at `battery_mah * charge_fraction` (`initial_charge_mah`). Battery-aware algorithms read `node.battery_fraction` (against the capacity; dividing by the starting charge would show every phone at 100 % on arrival) — don't reimplement it, while `energy_consumed_mah` counts from `initial_charge_mah`.
- **`is_active` has multiple causes, `battery_depleted` has one.** `is_active=False` means "not currently eligible for BLE/traffic" for any reason — battery death, not-yet-arrived, or departed (churn). `battery_depleted=True` means specifically "died from battery". The report's `dead_node_count` must read `battery_depleted`, not `not is_active`, or churn departures get miscounted as battery deaths. `on_site` is the person, not the phone: only churn clears it, and `_mobile_process` moves every node on site, so a dead phone's owner keeps walking (and leading their group).

### Conventions

- Python 3.9 floor: no `X | Y` union syntax, no `match` statements, no bare builtin generics — use `typing.Optional/List/Dict/Set/Tuple`.
- No comments except non-obvious WHY; no docstrings. The few existing comments (e.g. in `mobility/base.py`, `beacons.py`) mark deliberate injection points — keep that convention for new ones.
- One file per responsibility; SimPy-driven modules (`network.py`, `traffic.py`) deliberately take `env` structurally rather than importing `simpy` at module level, to stay independently testable.
